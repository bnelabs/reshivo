# Engineering-note to joint-check feasibility protocol

`engineering-intake-v1`, frozen before this task's manual entry and live calls. Three visible, developer-authored synthetic snapshots of one job live in `examples/engineering-intake-task-v1.json`. They are a diagnostic feasibility test, not unseen generalization or a human study. No material was processed. This test addresses the setup burden hidden by the previous prefilled demo, not numerical/scientific novelty.

## Inputs and arms

All arms receive the same existing brief, numeric case context and note. The initial numeric details are blank; the target is already stated in the user's brief. The initial note states a complete assembly, its mass/centre and bounds, coordinate meaning, two trim locations and their bounds/stocks, total stocks and a command increment. Mixed g/kg and cm/mm are deliberate. The second snapshot has a new observation of the same product; the third explicitly lacks its centre uncertainty. The latter two receive the same fixed, canonical post-initial targets to isolate observation intake rather than silently repair earlier failures. They are not an independently measured physical before/after sequence.

- **Manual app:** the current empty calculation path, with all common configuration retained when valid. Enter the already supplied note's quantities by existing labelled controls. Do not clear shared fields merely to inflate the baseline. Record actual control actions and successful downloads, including the third snapshot's deliberate missing bound. The common product/material prose is prepared once for every arm and excluded from completion counts. Expanders, selections, confirmations, corrections, entry actions and calculation requests count; inspection/screenshot/QA downloads do not. Report excluded preparation and note authorship explicitly. Do not interpret automation latency as human speed.
- **Ordinary Meta:** one structured extraction call per snapshot receives the same context and a strong field/units/unknowns prompt, without source-excerpt requirements. It returns the same 25 normalized fields. Its actual output goes to the same bound numerical checker with the same explicit review/independence choices in the harness. Do not force field-by-field copy into the app or give the helper an easier import path. Headless calls do not measure human review/control actions.
- **Reviewed adapter:** the actual production function, one call per snapshot, drafts source-linked fields. Code validates exact source occurrence, signed quantities and conversions. Targets already entered numerically remain canonical; conflicts require an explicit choice. A missing new observation bound cannot be inherited from an old observation. Source checks establish literal support, not correct interpretation. User review and independent-adjustment confirmation are required before preparing a bound request.

Both model arms use the configured model, low reasoning and 4,096 completion tokens, one call each per snapshot, no retries or score feedback. Alternate their order. Preserve prompts, schemas, raw responses, usage, timings, failures and every attempt; no authorization headers or credentials. Freeze designated implementation/fixture/protocol hashes before live calls. An interrupted run is incomplete. Changes after observing outputs require a new version/run; do not silently tune a failed baseline.

## What to score

Score normalized semantics before adapter validation, and accepted fields/completion separately. Check all available numeric/string/provenance fields, unknowns incorrectly filled, missing expected values, corrections, typed/provider failures and whether the same numerical model receives the intended case. Coordinate prose may be an exact source excerpt with equivalent datum/axis meaning; retain the words for review rather than requiring an arbitrary reference string. Existing canonical numeric targets need not be re-extracted when unchanged.

The first two snapshots must yield actual feasible joint checks with the expected rounded commands, with an independent forward corner check. The third must remain incomplete specifically for the missing centre uncertainty; it must not produce a joint performance result. A correct draft is not a physical measurement or a guarantee.

Acceptance for UI integration: one actual note can prepare the complete initial checked request, the new observation produces a revised request without reselecting material/product, and the missing bound remains missing. Only then build a compact review/apply path and measure its actual entry actions against the observed manual path. If it needs another long form or as many corrections as manual setup, stop this expansion. If ordinary Meta matches it, report that result; any observed advantage is app convenience and inspectable execution, not unique AI intelligence. No prize, general human-effort or physical-performance claim follows from three visible notes.
