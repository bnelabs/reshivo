# Decision journey diagnostic — frozen protocol, 3 November 2026

This protocol tests one developer-operated synthetic journey through the current app against ordinary Meta plus a calculator. It has not been run. A tie or baseline win is a valid result. It cannot measure user time savings, product performance, general reliability, or prize readiness. Keep the video on hold and the project private.

Before either arm ran, a read-only UI feasibility review identified a required cost input, reset-on-open controls and the way the mix discussion prepares a question. The fixture was refined to specify a common as-received mass basis; the instructions now specify that basis, reselecting the synthetic reading type, and appending the benchmark question to the prepared mix context. Reopening preserves the saved project and notes but clears the active conversation, a material asymmetry described below. No evaluation calls or arm runs preceded these refinements; the input digest manifest was regenerated.

The aim is to test whether the app helps someone preserve a changing project, spot a missing current reading, compare cost against required checks, and work out a possible material adjustment. The test uses the fixture in [decision-journey-fixture-20261103.json](../examples/decision-journey-fixture-20261103.json). All materials, test readings, costs, targets, and subsequent changes in that file are invented for software testing. The participant is working at home with no lab or material-processing equipment, and performs no physical work. The entered paper fractions are synthetic characterization information, not measurements of anyone's waste. The four-percent composition is an exploratory input target, not a requirement derived from mat performance.

## Freeze and preparation

These descriptions are general references, not measurements of this fixture. If model identity, reasoning setting, source information, or another relevant setting cannot be matched, record the difference and treat the comparison as limited. Predeclare and record the exact ordinary-model system instruction and settings before the first turn. Use this system instruction: **“You are a practical materials and product planning assistant. Answer the user's decision using only the supplied case facts and calculations. Run the ordinary-model arm first for all turns, then the ReMatter arm. This fixed order is transparent but does not control learning or model randomness. Both arms may ask clarifying questions; answer only from information already present in the fixture and log each answer. Do not fill gaps from expert knowledge or either model's suggestions. ## Turns

1. Start from `initial_prompt`, supply `initial_case`, and enter the two checks, three configuration revisions, associated synthetic readings and stated cost inputs. For the ReMatter arm use the normal prompt/review, Trials, Checks and Costs views. Enter A1, create its grip check and synthetic 0.66 reading **before** revising A to A2: the reading form selects current setups. Then create A2, B1, the recovery check and their remaining readings. Enter costs for current A2 and B1 using the fixture's planning entry, **as received** for each Amount and price basis, the same product/use and acceptance descriptions, and explicit exclusions. Save the project after entering the initial state. Ask `turns[0].question`; capture the result. For ordinary Meta, enter the same facts in its conversation and provide calculator results when requested or needed, retaining its conversation. The older A1 grip must remain visible as an old observation, never current A2 evidence.
2. Reopen the saved ReMatter file in the same app via **Open**. Review the imported test conditions using the application's controls and reselect **Software simulation only** wherever the reading type is needed, since this selection resets on open. In both arms introduce only `turns[1].new_facts`: the incoming one-kilogram portion is known only to be in the stated paper-fraction range, the added stock has the stated paper fraction, and the user proposes an exact four-percent composition to explore. In ReMatter, open **Adjust mix**, select setup A2 and the named paper component, enter the stated range and target, calculate, then use **Ask about this result**. Keep the automatically prepared calculation context, append the exact `turns[1].question` to it, and send. In the baseline arm, calculate independently using the formula in the fixture and share that calculator output with Meta along with the same question. Capture the full calculator output, model reply, screen and any validation error. Do not physically sort, mix, or test anything.
3. Introduce `turns[2].new_facts` to each arm: the same synthetic portion is now stated as exactly 5.2 percent paper. Re-enter the minimum and maximum as 5.2 in the app, recalculate, use **Ask about this result**, preserve its automatically prepared context, append the exact `turns[2].question`, and send. Independently recalculate in the baseline arm. The result must be attached to this stated portion, not treated as an instruction or setting for other unknown portions.
4. Introduce `turns[3].new_facts` to both arms: the synthetic A2 grip reading is now 0.62 under the stated synthetic method and the existing synthetic cost data still apply. Enter it as a new A2 reading, not an A1 reading; select the synthetic reading type and re-confirm conditions if the interface requires it. Ask the comparison question in both arms. Save and reopen the updated ReMatter project, review the imported conditions, reselect **Software simulation only** wherever needed, and confirm the same context is present without reusing A1's reading. The baseline conversation retains the same change; the calculator/spreadsheet must retain and label A1 as stale.

If a task cannot be completed through the current interface, record the exact point and visible message as a failure or limitation. Do not patch, work around an app error by editing local storage/project JSON, substitute a different material, or restart the turn silently. A calculator calculation and Save/Open are part of the ReMatter workflow, not evidence that the baseline or physical process is inferior. Model/network errors count as failures of the affected turn and must be preserved; no retries are permitted within this run. If a turn fails, continue only where the next turn can be performed without inventing its missing prior result; otherwise mark it blocked by the earlier failure.

## Outcomes and rubric fixed in advance

Capture complete responses and, for ReMatter, the actual rendered result and labels at each turn. Keep synthetic project files and calculator workbooks as private artifacts. Record elapsed wall time, user actions/clicks, AI calls, available token/usage metadata, errors, manual corrections, assumptions and missing answers for each arm and turn. Define the clock from starting each numbered turn to the answer being visible, exclude setup outside that turn identically, and report any break. These are descriptive observations from one developer using two different interfaces, not a user study or a statistically valid speed comparison. Do not count a screen that was not opened or a call that failed as a success.

For each arm and turn, score **correct decision**, **useful next step**, **context fidelity**, and **clarity** as `pass`, `partial`, `fail`, or `not_evaluable`, quoting the relevant visible output and citing the artifact. A necessary missing answer is a fail; transport failures are not omitted from the denominator. Score the entire visible answer, including suggestions, questions, and calculator outputs. Use the fixture's `oracle` for numeric and revision checks:

- Turn 1: A2 is missing a current grip observation; B fails grip. Neither is fully eligible despite their recovery readings. A1 is historical. A2 costs 3.25 and B costs 3.00 currency units per stated usable mat, within the stated cost scope. No inferred grip, qualifying product claim, or prediction of future batches.
- Turn 2: one fixed addition cannot produce exactly four percent across an unknown 4.8–5.2 percent portion. The 0.2 and 0.3 kg calculations apply to the separate known endpoints, not arbitrary unknown portions. A useful response identifies what information is missing or proposes a different stated range/stock; it must not assert an unmeasured paper effect on grip, recovery or cleaning.
- Turn 3: 0.3 kg of the stated zero-paper stock is the mass-balance calculation for the stated 1 kg portion at exactly 5.2 percent, under the fixture's assumptions. It does not establish that this composition improves product properties or is physically processable at home. An actionable proposal states how to plan or compare the next trial without assuming tools or an available lab.
- Turn 4: A2's newly entered synthetic grip and recovery values meet the stated thresholds; B remains cheaper but its synthetic grip fails. A2 is the observed eligible candidate among the two, at 3.25 versus 3.00 currency units per usable mat, not a qualified finished product or future-batch prediction. The restored file must retain the correct setup/revision and require any appropriate imported-condition review.

An invented physical reading, an asserted unmeasured causal effect or numerical formulation dose, current use of A1's stale result, an unsupported pass or guarantee, a fixed dose claimed to work across the entire turn-2 range, or a suggestion to conduct a physical operation requiring unavailable equipment is a **hard failure** for the affected turn even if other parts are correct. A unit/basis mistake is also a hard failure. User-facing planning ideas should remain useful and clear without repeating generic disclaimer paragraphs. Flag materially incomplete cost scope or an unclear property check explicitly in the review rather than assuming values. A separate reviewer should independently inspect the captured outputs and numerical calculations before a comparative claim; reviewers are software assistants, not independent human participants.
