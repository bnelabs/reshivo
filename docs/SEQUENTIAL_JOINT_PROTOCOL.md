# Sequential mass-and-balance diagnostic, v1

Freeze this protocol, fixtures, harness and imported implementation hashes before live calls. The three synthetic cases have two successive identified observations each. No product or material was physically tested. These fixtures are developer-authored and the first two commands resemble previous examples; this is a narrow diagnostic, not a held-out test, user study or proof of generalization.

Both arms receive the same canonical shared case and current observation. The harness carries these stated inputs between observations; it does not measure browser state persistence, authoring, human review, interaction count or user time. Locations and stock remain applicable only because the fixtures state they are unchanged. Each new observation's mass, centre and bounds replace the previous reading. A missing centre uncertainty remains missing.

* `ordinary`: structured Meta requests. For complete input the same production calculator is run locally and its actual result is supplied as a strong calculator baseline; for missing input no calculator result is supplied. It can choose any action/commands or explicitly continue reasoning, up to four model turns. The calculator result is already supplied, so this arm has faster access to it than the workflow; this comparison cannot prove an advantage over an unassisted model.
* `workflow`: the production Meta tool runner requests and uses its own bound calculation, with a maximum of four model turns and 4,096 completion tokens per turn. For a missing bound the ordinary UI's deterministic precondition stops a numerical request; the harness reproduces that gate, which is not a live model call. It is a headless reproduction and does not establish that a browser was exercised.

Both arms have at most four model turns, 4,096 completion tokens per turn and 210 seconds. The ordinary arm receives the same solver output before calling Meta and can stop early or explicitly continue; a transport failure is never retried. It may propose any command rather than copying the solver's choice. Each decision is checked against the same independent Decimal corner-forward calculation and command increment, including per-location and combined availability. Infeasibility is scored only when the fixture has a separate arithmetic proof: even removing all available mass from the lowest possible observed mass cannot bring it below the maximum target. The missing-bound stage passes only when no numerical action is given. No equivalence, accuracy or provider-availability claim is inferred from a successful JSON response alone.

Arm order alternates by case. No automatic retries or post-result wording changes. Each attempt, request and raw returned data, timing, usage, error and tool trace is retained. An interrupted or changed-hash run is incomplete. Report per-stage and complete-two-stage success over all attempted cases, provider failures, model call counts and wall times; do not omit failures. A tie or baseline win is a valid result. Commands are simulated static rigid mass/moment calculations and do not establish material, retention, strength, acoustic, durability, tipping, future batch or finished-product performance.
